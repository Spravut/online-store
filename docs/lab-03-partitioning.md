# Часть 1. RANGE PARTITIONING по дате

```sql
CREATE TABLE events (
    id BIGSERIAL NOT NULL, user_id BIGINT NOT NULL,
    event_type VARCHAR(50) NOT NULL, payload TEXT, created_at TIMESTAMP NOT NULL
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_09_09 PARTITION OF events FOR VALUES FROM ('2026-09-09') TO ('2026-09-10');
CREATE TABLE events_2026_09_10 PARTITION OF events FOR VALUES FROM ('2026-09-10') TO ('2026-09-11');
CREATE TABLE events_2026_09_11 PARTITION OF events FOR VALUES FROM ('2026-09-11') TO ('2026-09-12');
```

Распределение 900 000 строк:

```
  partition_name   | count
-------------------+--------
 events_2026_09_09 | 299478
 events_2026_09_10 | 299858
 events_2026_09_11 | 300664
```

**1. Куда попадёт запись с `created_at = '2026-09-10 12:00:00'`?**
В `events_2026_09_10` — проверено вставкой, `tableoid::regclass` вернул именно её.

**2. Куда попадёт `created_at = '2026-09-11 00:00:00'`?**
В `events_2026_09_11`. Значение ровно на границе принадлежит **правой** партиции,
потому что нижняя граница включающая, а верхняя — нет.

**3. Что произойдёт при вставке за 2026-09-12?**

```
ERROR:  no partition of relation "events" found for row
DETAIL:  Partition key of the failing row contains (created_at) = (2026-09-12 10:00:00).
```

Вставка падает. Именно поэтому партиции нужно создавать **заранее**, а их наличие —
контролировать (части 10–11).

**4. Почему граница `TO ('2026-09-11')` не включает эту дату?**
Диапазон партиции — полуинтервал `[FROM, TO)`. Так соседние партиции стыкуются без
зазоров и без пересечений: `TO` одной равен `FROM` следующей. Если бы обе границы были
включающими, значение на стыке подходило бы сразу двум партициям.

# Часть 2. Partition pruning

**Запрос по ключу партиционирования:**

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*) FROM events WHERE created_at >= '2026-09-10' AND created_at < '2026-09-11';
```

```
 Finalize Aggregate (actual time=22.135..25.730 rows=1 loops=1)
   Buffers: shared hit=2433
   ->  Gather ...
         ->  Partial Aggregate ...
               ->  Parallel Seq Scan on events_2026_09_10 events (actual rows=149930 loops=2)
                     Filter: ((created_at >= ...) AND (created_at < ...))
                     Buffers: shared hit=2433
 Execution Time: 25.752 ms
```

- **Сколько партиций проверено:** одна.
- **Какая нужна:** `events_2026_09_10`.
- **Исключены ли остальные:** да, обе.
- **Где это видно:** две другие партиции просто **отсутствуют в плане**. Postgres не
  печатает «я их отбросил» — признаком pruning является то, что в дереве плана остался
  единственный узел сканирования вместо `Append` по всем партициям. Прочитано 2 433
  страницы вместо 7 303 у полного обхода.

**Запрос не по ключу партиционирования:**

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT COUNT(*) FROM events WHERE event_type = 'click';
```

```
 Finalize Aggregate (actual time=32.742..36.692 rows=1 loops=1)
   Buffers: shared hit=7303
   ->  Parallel Append (actual rows=75069 loops=3)
         ->  Parallel Seq Scan on events_2026_09_11 ...  Rows Removed by Filter: 75135
         ->  Parallel Seq Scan on events_2026_09_10 ...  Rows Removed by Filter: 112520
         ->  Parallel Seq Scan on events_2026_09_09 ...  Rows Removed by Filter: 224351
 Execution Time: 36.728 ms
```

**Почему второй запрос обращается ко всем партициям?**
`event_type` не входит в ключ партиционирования. Postgres знает границы партиций только
по `created_at`, поэтому не может доказать, что в какой-то из них нет строк с
`event_type = 'click'`. Приходится читать все — в плане появляется `Append`.

Правило: **pruning работает только для условий по ключу партиционирования.**

# Часть 3. RANGE PARTITIONING по числовому значению

```sql
CREATE TABLE products (id BIGINT, name TEXT, price NUMERIC) PARTITION BY RANGE (price);
CREATE TABLE products_cheap     PARTITION OF products FOR VALUES FROM (0) TO (100);
CREATE TABLE products_medium    PARTITION OF products FOR VALUES FROM (100) TO (1000);
CREATE TABLE products_expensive PARTITION OF products FOR VALUES FROM (1000) TO (MAXVALUE);
```

```
   partition_name   | count |   min   |   max
--------------------+-------+---------+---------
 products_cheap     |  2031 |    0.01 |   99.99
 products_medium    | 18051 |  100.04 |  999.97
 products_expensive | 79918 | 1000.11 | 4999.98
```

**Какие партиции просмотрит `WHERE price >= 100 AND price < 500`?**

```
 Seq Scan on products_medium products (actual time=0.007..1.943 rows=8025 loops=1)
   Filter: ((price >= '100'::numeric) AND (price < '500'::numeric))
   Rows Removed by Filter: 10026
 Execution Time: 2.176 ms
```

Только `products_medium`. Диапазон `[100, 500)` целиком лежит внутри границ
`[100, 1000)`, поэтому `cheap` и `expensive` отброшены на этапе планирования.

Обрати внимание на `Rows Removed by Filter: 10026` — внутри нужной партиции условие
всё равно проверяется построчно: партиция отсекает лишние **таблицы**, а не строки.
Чтобы отсечь и строки, нужен индекс.

# Часть 4. LIST PARTITIONING

```sql
CREATE TABLE customers (id BIGINT, name TEXT, customer_type VARCHAR(30))
PARTITION BY LIST (customer_type);
```

```
    partition_name    | count
----------------------+-------
 customers_b2c        | 30006
 customers_b2b        | 10047
 customers_enterprise |  9947
```

```
 Seq Scan on customers_b2b customers (actual time=0.005..0.886 rows=10047 loops=1)
   Filter: ((customer_type)::text = 'B2B'::text)
 Execution Time: 1.217 ms
```

- **Какая партиция используется:** только `customers_b2b`.
- **Почему не другие:** значение `'B2B'` явно перечислено в определении одной партиции,
  а список значений у партиций не пересекается — остальные гарантированно пусты
  по этому условию.
- **Отличие от RANGE:** RANGE отбрасывает партиции сравнением с границами интервала
  и работает для `<`, `>`, `BETWEEN`. LIST сравнивает значение со списком и работает
  для `=` и `IN`. RANGE подходит непрерывным величинам (дата, цена), LIST —
  дискретному справочнику с небольшим числом заранее известных значений.

# Часть 5. LIST: неизвестное значение и DEFAULT

```sql
INSERT INTO customers VALUES (100, 'Test User', 'VIP');
```

```
ERROR:  no partition of relation "customers" found for row
DETAIL:  Partition key of the failing row contains (customer_type) = (VIP).
```

После `CREATE TABLE customers_default PARTITION OF customers DEFAULT;` та же вставка
проходит, строка попадает в `customers_default`.

**1. Зачем нужна DEFAULT partition?** Это «мусорная корзина» для значений, не подошедших
ни одной партиции. Без неё появление нового типа клиента роняет вставку.

**2. Чем полезна?** Превращает жёсткий отказ в мягкий: сервис продолжает работать, а
данные не теряются. Появление строк в DEFAULT — сигнал, что схему пора расширить.

**3. Какие проблемы, если складывать всё в DEFAULT?**

- DEFAULT растёт неограниченно и превращается в ту самую большую таблицу, ради борьбы
  с которой затевалось партиционирование;
- запросы по новым значениям всегда идут в DEFAULT без всякого pruning;
- **добавить новую партицию становится дорого**: Postgres обязан просканировать DEFAULT
  целиком, чтобы убедиться, что в нём нет строк, которые должны были попасть в новую
  партицию, и на это время берётся тяжёлая блокировка;
- проблема маскируется: вместо явной ошибки получаем тихую деградацию.

Поэтому DEFAULT — страховка, а не решение. Наличие строк в ней должно мониториться.

# Часть 6. HASH PARTITIONING

```sql
CREATE TABLE user_events (...) PARTITION BY HASH (user_id);
CREATE TABLE user_events_0 PARTITION OF user_events FOR VALUES WITH (MODULUS 4, REMAINDER 0);
-- ... 1, 2, 3
```

Распределение 1 000 000 строк:

```
 partition_name | count  |  pct
----------------+--------+-------
 user_events_0  | 251335 | 25.13
 user_events_1  | 249488 | 24.95
 user_events_2  | 249682 | 24.97
 user_events_3  | 249495 | 24.95
```

**1. Насколько равномерно?** Практически идеально: отклонение от 25 % не превышает 0,13
процентного пункта. Хэш-функция размазывает значения независимо от их распределения.

**2. Почему HASH полезен?** Он решает задачу, с которой RANGE не справляется: равномерно
разложить данные по нескольким физическим разделам, когда естественного диапазона нет.
Это база для шардирования и для распараллеливания нагрузки: ни одна партиция не
становится «горячей».

**3. Чем отличается от RANGE?** RANGE сохраняет порядок — соседние значения лежат рядом,
поэтому работают диапазонные запросы. HASH порядок уничтожает намеренно. Точечный запрос
по ключу партиционирования при HASH прунится:

```
 -> Parallel Seq Scan on user_events_0 user_events   -- WHERE user_id = 12345
      Rows Removed by Filter: 125662
 Execution Time: 11.774 ms
```

А диапазонный запрос по другой колонке — нет, читаются все четыре партиции.

**4. Почему HASH плохо подходит для «удалить данные старше 3 лет»?** Потому что строки
за любую дату равномерно размазаны по всем партициям. Ни одну партицию нельзя отцепить
целиком: придётся делать `DELETE ... WHERE created_at < ...` по всем разделам — то есть
ровно ту дорогую операцию, которой партиционирование должно было избежать. Для этого
сценария нужен RANGE по дате, где старый период — это отдельная таблица, и её достаточно
отсоединить.

# Часть 7. Выбор стратегии

| Сценарий | Стратегия | Обоснование |
|---|---|---|
| **A.** Миллионы событий в день, через 3 года удалять старое | **RANGE по дате** (день или месяц) | Удаление превращается в `DETACH PARTITION` + `DROP TABLE` — операция над метаданными вместо `DELETE` миллиардов строк с последующим `VACUUM`. |
| **B.** Пользователи B2C / B2B / Enterprise, фильтрация по типу | **LIST по `customer_type`** | Значений мало, они дискретны и заранее известны; каждый запрос с `WHERE customer_type = ?` попадает ровно в одну партицию. |
| **C.** Равномерно распределить по `user_id` | **HASH по `user_id`** | Естественных границ у идентификатора нет, а хэш даёт равномерность (измерено: 24,95–25,13 %) и отсутствие горячих разделов. |
| **D.** Аналитика по `created_at BETWEEN ...` | **RANGE по `created_at`** | Диапазонные условия — единственный случай, где pruning отсекает партиции пачками; читается только нужный период. |
| **E.** Платежи по странам EE / LV / LT / FI / SE | **LIST по коду страны** | Конечный справочник значений; плюс удобно для регионального хранения и требований по локализации данных. Обязательно с DEFAULT — появится шестая страна. |

# Часть 8. Партиционирование и индексы

```sql
CREATE INDEX idx_events_user_id ON events (user_id);
```

Индекс создаётся на **родительской** таблице, и Postgres автоматически материализует его
в каждой партиции:

```
     tablename     |           indexname
-------------------+-------------------------------
 events            | idx_events_user_id              -- «виртуальный» родительский
 events_2026_09_09 | events_2026_09_09_user_id_idx
 events_2026_09_10 | events_2026_09_10_user_id_idx
 events_2026_09_11 | events_2026_09_11_user_id_idx
```

Запрос с условиями по обоим механизмам:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM events
WHERE created_at >= '2026-09-10' AND created_at < '2026-09-11' AND user_id = 12345;
```

```
 Bitmap Heap Scan on events_2026_09_10 events (actual time=0.065..0.070 rows=4 loops=1)
   Recheck Cond: (user_id = 12345)
   Filter: ((created_at >= ...) AND (created_at < ...))
   Heap Blocks: exact=4
   Buffers: shared hit=7 read=3
   ->  Bitmap Index Scan on events_2026_09_10_user_id_idx (actual time=0.059..0.059 rows=4)
         Index Cond: (user_id = 12345)
 Execution Time: 0.109 ms
```

**1. Какие партиции отфильтрованы:** две из трёх, в плане осталась только
`events_2026_09_10`.
**2. Используется ли индекс:** да, `events_2026_09_10_user_id_idx`.
**3. На каком уровне существует индекс:** физически — в каждой партиции своё дерево;
на родителе живёт лишь «зонтичное» определение, которое гарантирует, что индекс появится
и в будущих партициях.
**4. Почему комбинация эффективнее одного механизма:** они отсекают разное.
Партиционирование выбрасывает целые **таблицы** по ключу партиционирования, индекс внутри
оставшейся таблицы выбирает нужные **строки**. По отдельности: только партиции — пришлось
бы просканировать все 300 тыс. строк дня; только индекс — дерево строилось бы по всем 900
тыс. строк и было бы втрое выше. Вместе получилось 0.109 мс и 10 прочитанных страниц.

Дополнительный практический плюс: индекс каждой партиции меньше, а значит перестраивается
и обслуживается `VACUUM` быстрее и по частям.

# Часть 9. Когда партиционирование не помогает

```sql
SELECT COUNT(*) FROM events WHERE event_type = 'click';
```

| Вариант | План | Buffers | Execution Time |
|---|---|---|---|
| до индекса | `Parallel Append` + 3 × `Seq Scan` | 7 303 | 36.728 мс |
| после `CREATE INDEX idx_events_event_type` | `Parallel Append` + 3 × `Bitmap Heap Scan` | 7 502 | 28.194 мс |

**Почему partitioning сам по себе не решил проблему?** Условие наложено на `event_type`,
а партиции нарезаны по `created_at`. Postgres не может исключить ни одну партицию, потому
что «кликов» не запрещено быть в любой из них. Партиционирование ускоряет только те
запросы, которые ограничивают ключ партиционирования.

Но и индекс здесь почти не помог: `event_type` имеет всего 4 значения, запрос возвращает
25 % таблицы. Прочитанных страниц стало даже **больше** (7 502 против 7 303) — добавилось
чтение самого индекса. Выигрыш 36.7 → 28.2 мс лежит в пределах разброса.

> **Вывод.** Партиционирование и индекс отвечают на разные вопросы.
> Партиционирование — «какие таблицы вообще не трогать», индекс — «какие строки внутри
> таблицы читать». Если запрос не ограничивает ключ партиционирования, первый механизм
> бесполезен. Если условие низкоселективно, бесполезен и второй. Этот запрос —
> случай, когда не работает ни один: помогла бы предагрегация счётчиков по типам событий.

# Часть 10. Автоматическое создание партиций

Реализовано в [`app/services/partitions.py`](../app/services/partitions.py) →
`ensure_partitions()`, CLI — [`scripts/partition_job.py`](../scripts/partition_job.py).

```
docker compose exec backend python -m scripts.partition_job create
```

Лог полностью повторяет формат из задания:

```
Partition job started. Table: events, horizon: 3 day(s)
Existing partitions: 3
Required partitions: 4
Missing partitions: 3
Creating: events_2026_09_13 [2026-09-13 .. 2026-09-14)
Partition created successfully.
Creating: events_2026_09_14 [2026-09-14 .. 2026-09-15)
Partition created successfully.
Creating: events_2026_09_15 [2026-09-15 .. 2026-09-16)
Partition created successfully.
Partition job finished. Created: 3
```

Как выполнены требования:

| Требование | Как реализовано |
|---|---|
| создаёт недостающие | вычисляет требуемый набор `required_partitions()` и сравнивает с фактическим из `pg_inherits` |
| не создаёт существующие | сравнение по множеству имён + `CREATE TABLE IF NOT EXISTS` как вторая линия защиты |
| безопасна при повторном запуске | идемпотентна: второй запуск подряд печатает «создавать нечего» |
| логирует результат | построчный лог каждого шага, в конце — сколько создано |

Имена и границы строятся из одной функции `partition_bounds()`, поэтому job и health check
никогда не разойдутся в том, какая партиция считается нужной. Поддерживаются две
гранулярности: `day` (учебная `events`) и `month` (боевая `orders`).

Имена таблиц подставляются через `psycopg.sql.Identifier`, границы — через `sql.Literal`,
склейки строк в SQL нет.

# Часть 11. Production-сценарий: job сломался

## 11.1. PartitionHealthCheck и уведомление

`check_partitions()` сравнивает требуемый набор с фактическим и возвращает `OK` либо
`CRITICAL`. Полный сценарий, выполненный вживую:

**Шаг 1 — партиции на будущее отсутствуют:**

```
2026-09-12 11:28:23 ERROR PartitionHealthCheck: CRITICAL, отсутствуют партиции:
                    events_2026_09_13, events_2026_09_14, events_2026_09_15
Результат проверки: CRITICAL
Ожидается партиций: 4
  OK  events_2026_09_12
  !!  events_2026_09_13
  !!  events_2026_09_14
  !!  events_2026_09_15
Уведомление отправлено в Telegram
```

В Telegram пришло:

```
🚨 Partition alert

Table: events
Missing partitions: events_2026_09_13, events_2026_09_14, events_2026_09_15
Expected horizon: 3 days
Checked at: 2026-09-12 11:28:23
```

**Шаг 2 — повторная проверка сразу же:**

```
Статус не изменился — уведомление не отправлялось (защита от спама)
```

**Шаг 3 — job создаёт партиции, проверка возвращает OK:**

```
🟢 Partition check OK

Table: events
All required partitions exist.
Checked at: 2026-09-12 11:28:33
```

## 11.2. Проверка, что alert действительно работает

Сбой воспроизводится специальной командой — она нужна именно для демонстрации:

```bash
docker compose exec backend python -m scripts.partition_job break --partition events_2026_09_15
```

```
Партиция events_2026_09_15 удалена — теперь проверка должна вернуть CRITICAL
```

Последующий `check` вернул `CRITICAL`, отсутствующей была названа ровно удалённая
партиция, уведомление пришло. Повторный `check` промолчал.

## 11.3. Восстановление

`create` пересоздал партицию, `check` вернул `OK` и прислал recovery-сообщение.

## 11.4. Защита от повторных алертов

Уведомление отправляется **только при смене статуса**:

| Было | Стало | Действие |
|---|---|---|
| OK | CRITICAL | 🚨 alert |
| CRITICAL | CRITICAL | тишина |
| CRITICAL | OK | 🟢 recovery |
| OK | OK | тишина |

Последний статус хранится не в памяти процесса, а в таблице `partition_alert_state`:

```
 table_name | status | details |     changed_at
------------+--------+---------+---------------------
 events     | OK     |         | 2026-09-12 11:28:51
 orders     | OK     |         | 2026-09-12 11:47:50
```

Благодаря этому защита от спама переживает перезапуск контейнера, а `changed_at`
обновляется только при реальной смене статуса — по нему видно, как долго система
находится в текущем состоянии.

## 11.5. Как устроены секреты

Токен бота и `chat_id` читаются только из переменных окружения
`TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID`. Их место — файл `.env`, который добавлен
в `.gitignore`; в репозитории лежит [`.env.example`](../.env.example) с заглушками.
В `docker-compose.yml` они пробрасываются как `${TELEGRAM_BOT_TOKEN:-}`, поэтому без

Клиент Telegram ([`app/alerts.py`](../app/alerts.py)) никогда не бросает исключение
наружу: падение алертинга не должно ронять job, который его вызвал.

# Часть 12. Партиционирование собственной базы

## Шаги 1–4. Таблица, ключ, стратегия и обоснование

| Решение | Значение |
|---|---|
| Таблица | `orders` |
| Ключ | `created_at` |
| Стратегия | `RANGE` |
| Гранулярность | месяц |

**Почему именно эта таблица?** Это единственная таблица-журнал в схеме. `users`,
`products`, `categories` ограничены числом клиентов и ассортиментом, а заказы
накапливаются непрерывно и никогда не удаляются: 5 000 300 строк, 464 МБ данных
и 834 МБ индексов — больше, чем всё остальное вместе.

**Почему именно этот ключ?** У заказа есть естественная ось времени, и почти все
запросы к истории её используют: лента заказов сортируется по `created_at DESC`,
аналитика считает продажи за период, отчёты строятся по месяцам. Плюс это единственный
атрибут, по которому данные естественно «стареют»: заказы прошлого года читают редко,
а удалять их когда-нибудь придётся целыми периодами.

**Почему RANGE?** LIST не подходит — у даты нет конечного списка значений. HASH размазал
бы каждый месяц по всем партициям и убил бы и pruning по периоду, и возможность отцепить
старое. RANGE по месяцу даёт партиции по ~200 тыс. строк: достаточно крупные, чтобы их
не стало сотни, и достаточно мелкие, чтобы месячный отчёт читал одну.

**Какие запросы должны выиграть от pruning?** Всё, что ограничивает `created_at`:
`GET /api/orders?from=&to=`, аналитика за период, лента заказов с сортировкой по дате.

## Шаг 5. Партиции

Миграция [`migrations/004_orders_partitioned.sql`](../migrations/004_orders_partitioned.sql)
создала **32 партиции**: 25 месяцев существующих данных (2024-09 … 2026-09), 6 месяцев
вперёд и `orders_default`.

```
 orders_2026_12   FOR VALUES FROM ('2026-12-01 00:00:00+00') TO ('2027-01-01 00:00:00+00')
 orders_2027_01   FOR VALUES FROM ('2027-01-01 00:00:00+00') TO ('2027-02-01 00:00:00+00')
 ...
 orders_default   DEFAULT
```

Перенос 5 млн строк занял **3 минуты 11 секунд**. Данных в `orders_default` — 0,
то есть все строки легли в свои месяцы.

Побочный эффект пересоздания таблицы — она стала компактнее: **388 МБ данных и 626 МБ
индексов** против 464 и 834 МБ до миграции. Причина в том, что данные записаны заново,
без накопленного bloat, а индексы каждой партиции строились с нуля.

### Что пришлось изменить в схеме

**Первичный ключ.** У партиционированной таблицы PK обязан включать ключ
партиционирования, поэтому он стал составным: `PRIMARY KEY (id, created_at)`.
Глобальная уникальность `id` на уровне СУБД больше не гарантируется — она держится на
том, что значения выдаёт одна последовательность.

**Внешний ключ.** `order_items.order_id REFERENCES orders(id)` ссылался на цель,
которой больше не существует, и ограничение пришлось снять. Это реальная цена
партиционирования, а не оплошность: целостность теперь обеспечивается на уровне
приложения — позиции всегда создаются вместе с заказом в одной транзакции
([`app/services/orders.py`](../app/services/orders.py)).

## Шаг 6. Проверка запросов

Все замеры — на 5 000 300 заказах, до и после миграции.

| Запрос | Endpoint | До | После | Pruning |
|---|---|---|---|---|
| Q1 диапазон дат | `GET /api/orders?from=&to=` | 0.301 мс | **0.212 мс** | ✅ 1 партиция из 32 |
| Q2 по идентификатору | `GET /api/orders/{id}` | 0.181 мс | **1.382 мс** | ❌ все 32 |
| Q3 по пользователю | `GET /api/users/{id}/orders` | 0.828 мс | **2.158 мс** | ❌ все 32 |
| Q4 агрегация за месяц | `GET /api/analytics/sales-by-category` | 1 735.9 мс | 1 661.5 мс | ✅ частично |

**Q1 — pruning работает.** В плане осталась ровно одна партиция:

```
 Limit (actual time=0.023..0.158 rows=20 loops=1)
   ->  Index Scan using orders_2026_08_created_at_idx on orders_2026_08 o
         Index Cond: ((created_at >= '2026-08-01+00') AND (created_at < '2026-09-01+00'))
 Execution Time: 0.212 ms
```

**Q2 — стало хуже в 7,6 раза.** Запрос по `id` не ограничивает `created_at`, поэтому
Postgres обязан заглянуть в каждую партицию. В плане — `Append` из 32 узлов:

```
 Append (actual time=0.659..0.858 rows=1 loops=1)
   ->  Index Scan using orders_2024_09_pkey on orders_2024_09 o_1 (actual rows=0)
   ->  Index Scan using orders_2024_10_pkey on orders_2024_10 o_2 (actual rows=0)
   ...   (всего 32 узла, из них 31 вернул 0 строк)
 Execution Time: 1.382 ms
```

**Q3 — хуже в 2,6 раза** по той же причине: `user_id` не является ключом
партиционирования, и `Merge Append` собирает результат из 32 индексов, чтобы сохранить
порядок `created_at DESC`.

**Q4 — почти не изменилась**, но по интересной причине: сторона `orders` теперь
прунится до пяти партиций вместо bitmap-скана по всей таблице, однако **узким местом
остаётся `order_items`** — она не партиционирована, и её 12,5 млн строк читаются
целиком. Это прямое продолжение вывода лабораторной №2: партиционировать надо было
и дочернюю таблицу тоже.

### Ради чего всё затевалось: удаление старых данных

```
 rows_in_2024_09 = 134 661

DELETE FROM orders WHERE created_at >= '2024-09-01' AND created_at < '2024-10-01';
DELETE 134661
Time: 58.474 ms

ALTER TABLE orders DETACH PARTITION orders_2024_09;
ALTER TABLE
Time: 31.637 ms
```

Разница во времени самих команд невелика, и это надо честно сказать. Главное отличие —
в последствиях: `DELETE` оставляет 134 661 мёртвую версию строки, которые потом должен
вычистить `VACUUM`, место на диске сразу не освобождается, индексы раздуваются.
`DETACH` — операция над метаданными, после неё таблицу можно просто удалить, мгновенно
вернув 12 МБ. На таблице в миллиард строк эта разница превращается в «часы против
секунд».

Отдельная деталь: `DETACH` занял 31 мс вместо ожидаемых долей миллисекунды, потому что
существует `orders_default` — Postgres обязан проверить, что в ней нет строк,
относящихся к отцепляемому диапазону. Ещё один аргумент держать DEFAULT пустой.

# Контрольные вопросы

**1. Что такое partitioning?** Физическое разделение одной логической таблицы на
несколько таблиц-партиций по значению ключа. Приложение работает с родительской
таблицей как с обычной, а Postgres направляет строки в нужную партицию и исключает
ненужные при чтении.

**2. Чем partitioning отличается от индекса?** Индекс отвечает на вопрос «какие **строки**
внутри таблицы читать», партиционирование — «какие **таблицы** вообще не трогать».
Индекс — дополнительная структура поверх тех же данных, партиционирование — другая
раскладка самих данных. Поэтому они дополняют друг друга (часть 8), а не заменяют.

**3. Какие стратегии поддерживает PostgreSQL?** `RANGE` (диапазоны), `LIST` (списки
значений), `HASH` (остаток от хэша). Плюс `DEFAULT`-партиция для RANGE и LIST,
и возможность многоуровневого партиционирования.

**4. Когда использовать RANGE?** Когда у данных есть непрерывная упорядоченная величина,
по которой идут запросы: дата, цена, номер. Особенно когда старые периоды нужно
удалять целиком.

**5. Когда использовать LIST?** Когда ключ — конечный справочник дискретных значений:
тип клиента, страна, статус. Значения должны быть известны заранее и не пересекаться.

**6. Когда использовать HASH?** Когда естественных границ нет, а нужно равномерно
распределить нагрузку и объём: партиционирование по `user_id`, подготовка к шардированию.

**7. Как выбрать partition key?** По тому, какие условия чаще всего встречаются в
`WHERE` — pruning работает только по ключу. Дополнительно: ключ должен давать партиции
сопоставимого размера, быть неизменяемым (смена значения приводит к физическому переносу
строки) и делить данные на разумное число частей.

**8. Что такое partition pruning?** Исключение партиций, заведомо не содержащих нужных
строк. Происходит на этапе планирования (когда границы известны из констант) или
выполнения (для параметров и подзапросов — в плане это `Subplans Removed`).

**9. Почему pruning может не сработать?** Условие не по ключу партиционирования
(часть 2, `event_type`); ключ спрятан в выражение или функцию; значение приходит
параметром, и план строится обобщённым; в условии есть `OR` по другой колонке;
существует DEFAULT-партиция, которую приходится проверять.

**10. Можно ли использовать индексы вместе с partitioning?** Да, и нужно. Индекс
создаётся на родительской таблице, и Postgres автоматически создаёт его в каждой
существующей и будущей партиции. Это измерено в части 8: pruning + индекс дали
0.109 мс и 10 страниц чтения.

**11. Что произойдёт, если подходящей партиции нет?** `INSERT` упадёт с ошибкой
`no partition of relation ... found for row`. Если есть DEFAULT — строка попадёт в неё.

**12. Зачем создавать будущие партиции заранее?** Потому что их отсутствие ломает не
чтение, а **запись** — падает `INSERT`, то есть пользовательская операция. Создавать
партицию в момент первой вставки поздно: ошибка уже произошла.

**13. Почему создание партиций должно быть автоматизировано?** Человек забудет, уйдёт в
отпуск или ошибётся в имени. Партиции нужны регулярно и предсказуемо — это работа для
job. Ручное создание также не воспроизводится при развёртывании новой среды.

**14. Чем логирование ошибки отличается от alerting?** Лог пассивен: он фиксирует факт,
но его нужно пойти и прочитать. Alert активен: он сам приходит к дежурному. Ошибка,
записанная в лог в 01:00 и прочитанная в 10:00 после падения приложения — это не
мониторинг.

**15. Что такое recovery alert?** Уведомление о возврате системы в норму. Без него
дежурный видит только «сломалось» и вынужден проверять вручную, починилось ли. Пара
alert/recovery закрывает инцидент и показывает, сколько он длился.

**16. Почему нельзя бесконечно отправлять одинаковый alert?** Канал превращается в шум,
и на него перестают реагировать — настоящая авария потеряется среди повторов. Поэтому
сообщение отправляется только при смене статуса, а факт проверки пишется в лог.

**17. Всегда ли partitioning ускоряет запросы?** Нет, измерено на своём сервисе:
`GET /api/orders/{id}` замедлился в 7,6 раза, а `GET /api/users/{id}/orders` — в 2,6,
потому что эти запросы не ограничивают ключ партиционирования и вынуждены обходить все
32 партиции. Партиционирование ускоряет запросы по ключу и замедляет все остальные.

**18. Какие проблемы возникают при неправильном размере партиций?**
Слишком **мелкие**: сотни и тысячи партиций раздувают время планирования (планировщик
рассматривает каждую), растёт число файлов и объектов в каталоге, каждый запрос без
pruning обходит огромный `Append`. Слишком **крупные**: партиция сама становится той
большой таблицей, ради борьбы с которой всё затевалось, pruning отсекает мало, а
удаление старых данных теряет гранулярность. Ориентир — партиции сопоставимого размера
и их количество в пределах сотни-двух.
