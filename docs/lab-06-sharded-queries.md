# Лабораторная работа №6. Что происходит с backend-сервисом после шардирования

Продолжение лабораторной №5. Конфигурация та же: три шарда PostgreSQL 16,
shard key — `orders.user_id`, стратегия Consistent Hashing (150 виртуальных
узлов), 100 000 заказов и 249 785 позиций.

Все запросы ниже — реальные запросы сервиса из `app/repositories/` и
`app/sharding/queries.py`, а не учебные примеры.

---

## 1. Архитектура

```
                    Backend (FastAPI)
                          │
              ┌───────────┴───────────┐
              │                       │
         Router (app/sharding)   основная база
     ┌────────┼────────┐         users, products,
     ▼        ▼        ▼         categories, reviews
  Shard 0  Shard 1  Shard 2       + replica (лаб. №4)
  orders   orders   orders
  order_   order_   order_
  items    items    items
```

Что где лежит:

| Данные | Где | Почему |
|---|---|---|
| `orders`, `order_items` | шарды, по `user_id` | растущая сущность, 5 млн строк |
| `users`, `products`, `categories`, `reviews` | основная база | справочники, растут медленно |

Router (`app/sharding/router.py` + `pools.py`) — единственное место, которое
знает о существовании нескольких баз:

```python
@contextmanager
def connection_for(key: object) -> Iterator[Connection]:
    with shard_connection(route(key)) as conn:
        yield conn
```

Текущее состояние кластера видно через API:

```
$ curl localhost:8080/api/shards/
{"shard_count":3,"strategy":"consistent","virtual_nodes":150,
 "health":{"0":{"ok":true},"1":{"ok":true},"2":{"ok":true}}}
```

Все замеры ниже — медиана из 15 запусков.

## 2. Single-Shard Query

Запрос сервиса: список заказов пользователя.
Исходно — `app/repositories/orders.py: list_orders(user_id=...)`,
после шардирования — `app/sharding/queries.py: user_orders()`:

```python
def user_orders(user_id: int, limit: int = 50, offset: int = 0):
    shard_id = route(user_id)                      # <- один вызов router
    with connection_for(user_id) as conn, conn.cursor() as cur:
        cur.execute(
            """
            SELECT o.id, o.user_id, o.status, o.total_amount, o.created_at
            FROM orders o
            WHERE o.user_id = %s
            ORDER BY o.created_at DESC
            LIMIT %s OFFSET %s
            """,
            (user_id, limit, offset),
        )
```

Результат:

```
$ curl localhost:8080/api/shards/users/38/orders?limit=20
{"user_id":38,"shard":0,"shards_queried":1,"orders":[...]}
```

`shards_queried: 1`, медиана — **0.73 мс**.

План на шарде — обычный индексный доступ, никакой распределённости:

```
Limit  (cost=22.61..22.62 rows=5) (actual time=0.144..0.167 rows=9 loops=1)
  ->  Sort  (actual time=0.143..0.144 rows=9 loops=1)
        Sort Key: created_at DESC
        ->  Bitmap Heap Scan on orders o (actual time=0.063..0.091 rows=9)
              Recheck Cond: (user_id = 38)
              ->  Bitmap Index Scan on idx_shard_orders_user_created
                    Index Cond: (user_id = 38)
```

### Почему запросу не нужно обращаться к другим shard'ам

Потому что `user_id` — это и условие запроса, и shard key. Router вычисляет
`route(38) = 0`, и это не эвристика, а та же самая функция, по которой запись
клали: `hash_key(38)` попадает на дугу кольца, принадлежащую shard 0.

Ключевое слово — **гарантия**. Заказ пользователя 38 физически не мог
оказаться на shard 1 или shard 2: при загрузке его адрес считался той же
функцией. Поэтому идти туда не просто необязательно — там заведомо пусто,
и опрос этих узлов был бы гарантированно бесполезной работой.

По этой же схеме работают ещё два запроса сервиса:

| Запрос | Эндпоинт | shards_queried | Медиана |
|---|---|---|---|
| Заказы пользователя | `/api/shards/users/{id}/orders` | 1 | 0.73 мс |
| Статистика пользователя (`COUNT`, `SUM`, `AVG`) | `/api/shards/users/{id}/stats` | 1 | 0.65 мс |
| Заказ с позициями (JOIN) | `/api/shards/users/{id}/orders/{oid}/items` | 1 | — |

Обратите внимание на вторую строку: агрегат `SUM/AVG/COUNT` тоже остался
single-shard. Агрегация становится распределённой не сама по себе, а когда
в запросе **нет shard key**.

## 3. Агрегирующий запрос

Запрос сервиса: сводка по статусам (`COUNT`, `SUM`, `AVG`, `GROUP BY`) —
аналог `sales_by_category` из `app/repositories/analytics.py`.
Реализация: `app/sharding/queries.py: revenue_by_status()`.

На каждом шарде выполняется обычный SQL:

```sql
SELECT status, COUNT(*) AS orders, COALESCE(SUM(total_amount), 0) AS revenue
FROM orders
GROUP BY status
```

А приложение складывает группы с одинаковым ключом:

```python
for result in outcome["results"]:
    for row in result["data"]:
        bucket = merged.setdefault(row["status"], {...})
        bucket["orders"]  += row["orders"]
        bucket["revenue"] += row["revenue"]
...
# AVG пересчитан из сумм, а не усреднён по шардам.
row["avg_order_amount"] = round(row["revenue"] / row["orders"], 2)
```

Результат `COUNT(*)` по всей системе:

```
$ curl localhost:8080/api/shards/orders/count
{"per_shard":{"0":32319,"1":33449,"2":34232},"total":100000,
 "shards_queried":3,"partial":false,"total_ms":3.56,"slowest_shard_ms":2.45}
```

```
Shard 0 → 32 319
Shard 1 → 33 449
Shard 2 → 34 232
        ↓ aggregation (в приложении)
       100 000
```

`GROUP BY status` после слияния:

| status | orders | revenue | avg |
|---|---|---|---|
| PAID | 20 028 | 5 059 493 719.93 | 252 621.02 |
| SHIPPED | 19 916 | 5 057 930 720.77 | 253 963.18 |
| DELIVERED | 20 154 | 5 057 795 467.70 | 250 957.40 |
| NEW | 20 056 | 5 047 511 649.08 | 251 670.90 |
| CANCELLED | 19 846 | 4 992 139 417.08 | 251 543.86 |

### 1. Можно ли выполнить такой запрос только на одном shard?

Нет. Ни один шард не знает общего числа заказов — у каждого только своя
треть, и `SELECT COUNT(*)` на shard 0 честно вернёт 32 319. Это не ошибка
и не «неполные данные» с точки зрения PostgreSQL: для него это вся таблица.
Чтобы получить 100 000, нужно опросить все три узла.

Отдельная тонкость — **какие агрегаты складываются, а какие нет**:

| Агрегат | Как объединять |
|---|---|
| `COUNT`, `SUM`, `MIN`, `MAX` | складываются напрямую |
| `AVG` | **нельзя** усреднять средние — считается как `SUM/COUNT` после слияния |
| `COUNT(DISTINCT ...)` | нельзя сложить вообще: одно значение может встречаться на нескольких шардах; нужен либо перенос всех значений в приложение, либо приблизительный подсчёт (HyperLogLog) |
| `percentile`, медиана | точно — только перенеся все строки |

В коде это видно явно: `revenue_by_status()` пересчитывает `AVG` из сумм.
Если бы шарды отдавали свои `AVG` и приложение их усредняло, при разном
числе заказов на шардах результат был бы просто неверным.

Обратная сторона: агрегат по `sales_by_category` из исходного сервиса
(`categories → products → order_items → orders`) после шардирования вообще
не выражается одним запросом — `categories` и `products` лежат в основной
базе, а `order_items` на шардах. Это уже случай из задания 4.

### 2. Где должны объединяться результаты?

В backend — ему единственному видны все шарды. В проекте это функция
`scatter()` (`app/sharding/queries.py`), через которую проходит каждый
распределённый запрос: она рассылает работу, собирает частичные ответы,
считает тайминги и отмечает упавшие узлы.

Альтернативы, которых здесь сознательно нет: отдельный слой-координатор
(Citus, Vitess) или postgres_fdw с внешними таблицами. Оба переносят
слияние на уровень СУБД, но добавляют компонент, который тоже надо
эксплуатировать. Для учебного сервиса слияние в приложении нагляднее — весь
механизм умещается в одной функции.

### 3. Что происходит со временем выполнения при увеличении числа shard'ов?

Замер на реальных данных (`COUNT(*)`, медиана из 15 запусков):

| Шардов | Параллельно | Последовательно |
|---|---|---|
| 1 | 1.53 мс | 1.71 мс |
| 2 | 2.57 мс | 3.36 мс |
| 3 | 3.96 мс | 5.43 мс |

Здесь виден **последовательный** рост даже в параллельном режиме. Причина:
сам запрос на шарде занимает доли миллисекунды, поэтому в замере доминируют
накладные расходы fan-out — взятие соединения из пула, создание потоков, GIL.
При такой пропорции параллелизм даёт всего ~1.4×.

Чтобы отделить накладные расходы от эффекта параллелизма, тот же эксперимент
с заведомо тяжёлым запросом (`pg_sleep(0.1)` на каждом шарде):

| Шардов | Параллельно | Последовательно |
|---|---|---|
| 1 | 102.1 мс | 102.3 мс |
| 2 | 103.5 мс | 204.9 мс |
| 3 | 103.7 мс | 306.8 мс |

Вот здесь картина чистая:

- **последовательный обход — это сумма**: 100 → 200 → 300 мс, линейный рост;
- **параллельный — это максимум**: 102 → 103 → 104 мс, почти константа.

Именно поэтому `scatter()` опрашивает шарды через `ThreadPoolExecutor`:

```python
with ThreadPoolExecutor(max_workers=len(targets)) as executor:
    results = list(executor.map(run_one, targets))
```

Но «почти константа» — не бесплатно и не навсегда:

- время равно **самому медленному** шарду, а не среднему. С ростом числа
  узлов растёт вероятность, что хотя бы один окажется занят (эффект
  «хвостовых задержек»);
- нагрузка на кластер растёт линейно: 3 шарда = 3 полных `Seq Scan` вместо
  одного. Время ответа держится, а суммарная работа умножается;
- backend держит N одновременных соединений на каждый такой запрос.

Практический вывод: распределённая агрегация масштабируется по времени, но
не по стоимости. Если она нужна часто — её считают заранее и хранят
материализованной, а не собирают на лету.

## 4. JOIN между shard'ами

В сервисе есть JOIN-ы двух разных видов, и шардирование разводит их по
разным полюсам.

### Случай А: JOIN, который остался локальным

`orders JOIN order_items` — позиции заказа
(`app/repositories/orders.py: list_items`):

```sql
SELECT o.id, oi.product_id, oi.quantity, oi.price_at_purchase
FROM orders o
JOIN order_items oi ON oi.order_id = o.id AND oi.user_id = o.user_id
WHERE o.user_id = %s
```

Работает обычным SQL на одном шарде:

```
Nested Loop  (actual time=0.084..0.549 rows=19 loops=1)
  ->  Bitmap Heap Scan on orders o  (actual time=0.063..0.092 rows=9)
        ->  Bitmap Index Scan on idx_shard_orders_user_created
              Index Cond: (user_id = 38)
  ->  Index Scan using idx_shard_order_items_order on order_items oi
        Index Cond: (order_id = o.id)
Execution Time: 0.855 ms
```

Это не случайность, а результат проектного решения: при загрузке позициям
проставляется тот же shard key, что и у заказа
(`migrations_shard/001_shard_init.sql`):

```sql
CREATE TABLE order_items (
    ...
    user_id BIGINT NOT NULL,   -- тот же shard key, что у заказа
    FOREIGN KEY (order_id) REFERENCES orders (id) ON DELETE CASCADE
);
```

Обратите внимание: FK здесь **работает** — обе таблицы на одном узле.
Это единственный FK, уцелевший после шардирования.

### Случай Б: JOIN, который стал распределённым

`orders JOIN users` — заказ вместе с покупателем
(`app/repositories/orders.py: get_header_with_user`):

```sql
SELECT o.*, u.email, u.full_name
FROM orders o
JOIN users u ON u.id = o.user_id
WHERE o.id = %s
```

Где что лежит:

```
Shard 0/1/2          основная база
orders               users
  │                     │
  └──────── JOIN ───────┘   <- разные PostgreSQL
```

Реализация — `app/sharding/queries.py: recent_orders_with_users()`,
JOIN выполняется в три шага в приложении:

```python
orders_page = recent_orders(limit)                  # 1. scatter-gather по шардам
user_ids = sorted({row["user_id"] for row in rows}) # 2. собрали ключи
with main_connection(readonly=True) as conn, conn.cursor() as cur:
    cur.execute("SELECT id, email, full_name, city FROM users WHERE id = ANY(%s)",
                (user_ids,))                        # 3. один запрос в основную базу
users = {row["id"]: row for row in cur.fetchall()}
for row in rows:                                    # 4. склейка по ключу
    row["user_email"] = users.get(row["user_id"], {}).get("email")
```

Замер:

```
$ curl localhost:8080/api/shards/orders/recent-with-users?limit=20
{"join_performed_in":"application","shard_roundtrips":3,
 "extra_roundtrips":1,"user_ids_transferred":20}
```

Медиана — 2.98 мс, четыре round-trip вместо одного запроса.

### Ответы

**1. Что произойдёт, если связанные записи находятся на разных shard'ах?**

СУБД их не соединит. Для PostgreSQL, где лежит заказ, таблицы `users`
просто не существует — запрос упадёт на `relation "users" does not exist`.
JOIN приходится выполнять вручную в приложении: забрать левую сторону,
вытащить из неё ключи, отдельным запросом забрать правую, склеить по ключу.
Фактически это hash join, написанный руками, — со всем, что из этого следует:
нет статистики, нет выбора алгоритма планировщиком, нет push-down условий.

Особенно неприятны следствия для семантики. `LEFT JOIN` в исходном
`user_stats` при ручной склейке нужно воспроизводить явно (`users.get(...)`
с `None`), а любые `WHERE` по правой таблице нельзя применить до склейки —
значит, с шардов приезжают строки, которые всё равно будут отброшены.

**2. Можно ли выполнить такой JOIN обычным SQL-запросом к одному PostgreSQL?**

Нет. Обойти это можно тремя способами, каждый со своей ценой:

- **денормализация** — положить `user_email`/`user_full_name` прямо в `orders`.
  Убирает JOIN, но данные дублируются и расходятся при обновлении профиля;
- **reference table** — держать копию `users` на каждом шарде. Работает, пока
  справочник маленький (20 тысяч строк — вполне), но нужна синхронизация;
- **postgres_fdw** — подключить `users` как внешнюю таблицу. Синтаксически
  получится один SQL, но данные всё равно поедут по сети, просто перекладывать
  их будет PostgreSQL, а не приложение.

В проекте выбран ручной JOIN: он честно показывает стоимость и не прячет
сетевые походы за синтаксисом.

**3. Какие данные пришлось бы передавать между shard'ами?**

В текущей реализации — **между шардами ничего**. Шарды друг с другом не
разговаривают вообще; всё сходится в backend. Передаётся:

- с шардов в backend — строки `orders` (в замере 20 строк, но при `LIMIT 100`
  приехало бы 300, см. задание 5);
- из backend в основную базу — список из 20 `user_id`;
- обратно — 20 строк `users`.

Плохой сценарий — JOIN без ограничения: чтобы соединить все 100 000 заказов
со всеми пользователями, пришлось бы перетащить в память приложения все
100 000 строк. Распределённый JOIN опасен не самим фактом, а объёмом
пересылки.

**4. Можно ли выбрать shard key так, чтобы этот JOIN чаще выполнялся внутри
одного shard?**

Он уже так выбран — и это главный аргумент в пользу `user_id`. Если бы
ключом был `orders.id`, локальным не остался бы ни один JOIN: позиции одного
заказа и сам заказ разъехались бы по разным узлам.

Дальше улучшать можно только шардированием `users` **тем же ключом**
(`users.id = orders.user_id` → одна и та же функция → пользователь и его
заказы на одном узле). Это классический приём: выбирать общий ключ
шардирования для всего «поддерева» данных вокруг одной сущности.

Но `orders JOIN products` (через `order_items`) локальным не станет никогда:
один товар встречается в заказах всех пользователей, то есть присутствует на
всех шардах одновременно. Для таких таблиц единственное решение — держать их
как reference table, копию на каждом узле.

## 5. ORDER BY + LIMIT

Запрос сервиса: лента последних заказов
(`app/repositories/orders.py: list_orders` с сортировкой по умолчанию):

```sql
SELECT ... FROM orders o ORDER BY o.created_at DESC LIMIT 100
```

Реализация — `app/sharding/queries.py: recent_orders()`:

```python
# с каждого шарда берём его top-N
cur.execute("SELECT ... FROM orders o ORDER BY o.created_at DESC, o.id DESC LIMIT %s", (limit,))
...
# сливаем и отрезаем первые N
merged = sorted(fetched, key=lambda r: (r["created_at"], r["id"]), reverse=True)[:limit]
```

```
Shard 0 → top 100
Shard 1 → top 100
Shard 2 → top 100
        ↓ merge (в приложении)
       top 100
```

Замер:

```
$ curl "localhost:8080/api/shards/orders/recent?limit=100"
{"rows_fetched":300,"rows_returned":100,"overhead_rows":200,
 "shards_queried":3,"partial":false,"total_ms":3.15}
```

**300 строк по сети ради 100 нужных** — 200 строк выброшены.

### Почему недостаточно получить первые 100 записей только с одного shard

Потому что на шардах нет никакого порядка по времени: `created_at` не
участвует в маршрутизации, и заказы всех дат перемешаны на всех трёх узлах.
Глобальные «сто самых свежих» могут целиком лежать на одном шарде, могут
распределиться 40/35/25 — заранее это неизвестно.

Взяв top-100 с shard 0, мы получим сто самых свежих **заказов shard 0**.
Если на shard 1 в это же время появилась сотня более свежих записей,
результат будет просто неверным, и никакой признак в ответе на это не
укажет.

Почему при этом достаточно взять именно top-100 с каждого, а не всё подряд:
глобальный top-100 не может содержать запись, которая не входит в top-100
своего шарда. Если запись оказалась 101-й на своём узле, значит на этом же
узле есть 100 более свежих — и до глобального сотого места она не дотянет.
Поэтому `LIMIT N` на каждом шарде — это корректно, а не эвристика.

**Цена — `N × число шардов` строк по сети.** При 3 шардах это 300 строк на
100 нужных, при 10 шардах — 1000 строк. Overhead растёт линейно с числом
узлов.

**Отдельно про пагинацию.** `LIMIT 100 OFFSET 10000` в распределённом виде
превращается в катастрофу: с каждого шарда нужно затребовать `LIMIT 10100`,
то есть 30 300 строк ради сотни. Это главный практический довод за
keyset-пагинацию (`WHERE created_at < :last_seen ORDER BY created_at DESC
LIMIT 100`) — она в распределённом варианте остаётся такой же дешёвой, как
и в обычном. В лабораторной №1 (задание 15) keyset уже выигрывал у OFFSET
на одной базе; после шардирования разрыв становится драматическим.

## 6. Отказ одного shard

Эксперимент проведён реально: `docker stop shop_shard2`.

```
Shard 0 ✓
Shard 1 ✓
Shard 2 ✗
```

Что показал сервис:

```
 "health":{"0":{"ok":true},"1":{"ok":true},"2":{"ok":false,"error":"пул не открыт"}}}
```

```
$ curl localhost:8080/api/shards/orders/count
{"per_shard":{"0":32319,"1":33449},"total":65768,"shards_queried":3,
 "partial":true,
 "failed":[{"shard":2,"ok":false,"ms":5.33,
```


### 1. Какие данные становятся недоступны?

Ровно треть: 34 232 заказа и 85 432 позиции, принадлежащие 6 836
пользователям, чьи `user_id` попали на дуги shard 2. Список этих
пользователей детерминирован — его можно вычислить router'ом, не обращаясь
к самому шарду.

Данные не потеряны, а именно недоступны: это отказ узла, а не потеря
volume'а.

### 2. Какие endpoint'ы перестанут работать?

| Endpoint | Поведение при отказе shard 2 |
|---|---|
| `/api/shards/users/{id}/orders`, где `route(id) = 2` | **503**, данных нет |
| `/api/shards/users/{id}/orders`, где `route(id) ≠ 2` | 200, работает нормально |
| `/api/shards/orders/count` | 200, но `partial: true` и неполная сумма |
| `/api/shards/orders/recent` | 200, `partial: true`, лента без заказов shard 2 |
| `/api/shards/orders/by-id/{id}` | 200, но заказ может «не найтись» |
| `/api/users`, `/api/products`, `/api/analytics/*` | работают: основная база не затронута |

То есть отказ бьёт по **двум третям** пользовательских запросов не вообще, а
по **одной трети** пользователей полностью. Это важное свойство
шардирования: отказ частичный, но для конкретного пользователя — полный.

Отдельно опасен предпоследний случай. `by-id` — распределённый поиск, и
отсутствие результата на живых шардах внешне неотличимо от «такого заказа
нет». Поэтому в ответе обязателен флаг `partial`, иначе сервис будет тихо
врать.

### 3. Продолжит ли работать остальная часть сервиса?

Да, и это видно в замерах: `users/38/orders` вернул 200 при лежащем shard 2.
Так получилось благодаря тому, как написан `scatter()`:

```python
except (ShardUnavailable, Exception) as exc:
    return {"shard": shard_id, "ok": False, "error": str(exc), "ms": ...}
...
return {"results": ok, "failed": failed, "partial": bool(failed), ...}
```

Ошибка одного шарда становится элементом ответа, а не исключением. Ответ
помечается `partial: true`, и потребитель сам решает, годятся ли ему
неполные данные.

Одна честная проблема всплыла при рестарте backend с лежащим шардом:

```
2026-09-18 21:56:11 ERROR app.sharding.pools: shard 2 недоступен: pool initialization incomplete after 20 sec
2026-09-18 21:56:11 INFO  app.sharding.pools: router: <ConsistentHashRouter shards=[0, 1, 2]>
```

Старт приложения занял на 20 секунд больше — столько пул ждал соединения.
Сервис поднялся и работал, но при большом числе шардов это ожидание надо
делать параллельным или асинхронным.

### 4. Что должен делать backend при обращении к недоступному shard?

Реализовано так:

**Single-shard запрос → 503, а не 500.** Запрос не сломан, просто нужный
кусок данных сейчас недоступен. Для этого низкоуровневая
`psycopg.OperationalError` превращается в доменную ошибку:

```python
    except psycopg.OperationalError as exc:
        raise ShardUnavailable(f"shard {shard_id} недоступен: {exc}") from exc
```

и обрабатывается в `app/main.py`:

```python
@app.exception_handler(ShardUnavailable)
async def shard_unavailable_handler(request, exc):
    return JSONResponse(status_code=503, content={"detail": str(exc), "partial": True})
```

**Распределённый запрос → частичный ответ с честным флагом.** Отдавать
`total: 65768` без пометки — худшее, что можно сделать: цифра выглядит
правдоподобно и молча искажает отчётность.

**Чего делать нельзя ни в коем случае — убирать упавший шард из кольца.**
Соблазн есть: убрал точки shard 2, и его ключи поедут к соседям, запросы
начнут отвечать 200. Но после возвращения узла router вернёт ключи обратно,
и всё, что записалось к соседям, станет невидимым. В логе выше видно, что
кольцо осталось трёхшардовым (`shards=[0, 1, 2]`) при двух живых узлах —
это правильное поведение.

### 5. Как можно повысить отказоустойчивость?

По убыванию эффекта:

1. **Реплика у каждого шарда.** Механизм уже написан в лабораторной №4:
   `pg_basebackup` + streaming replication + `connection(readonly=...)`.
   Применить его к шардам — значит на каждый шард поднять standby и при
   отказе primary переключать на него чтение. Это устраняет главный риск:
   сейчас каждый шард — единственная точка отказа для трети пользователей.
2. **Fail fast вместо ожидания.** Сейчас мёртвый шард выясняется по таймауту.
   Circuit breaker (несколько ошибок подряд → узел помечен «битым» на
   30 секунд, запросы к нему отклоняются сразу) убирает задержку и не даёт
   одному узлу подвешивать пул соединений.
3. **Деградация вместо отказа для распределённых запросов.** Уже сделано
   через `partial: true`; следующий шаг — кэшировать последний полный
   результат агрегатов и отдавать его с пометкой «данные на такое-то время».
4. **Health check и алерты.** Инфраструктура из лабораторной №3
   (`APScheduler` + `TelegramNotifier` + дедупликация по смене статуса)
   переиспользуется как есть: заменить проверку партиций на `probe_shards()`.

## 7. Hot Shard

```
Shard 0 → 10% запросов
Shard 1 → 15% запросов
Shard 2 → 75% запросов
```

### Возможные причины применительно к этому сервису

**Неудачный shard key.** Если бы ключом был `status` или `created_at`, весь
сегодняшний трафик шёл бы на один узел. `user_id` от этого защищает: новые
заказы равномерно размазаны по всем пользователям.

**Неравномерное распределение данных.** В проекте измерено и почти
отсутствует: 32.32 / 33.45 / 34.23 %, разброс 1.91 п.п. С `virtual_nodes=1`
было бы 77 / 9 / 14 % — вот там hot shard возник бы из-за одних только
данных.

**Популярный пользователь.** Самая реальная угроза. Фактические данные:

```
заказов на пользователя: min=1  max=20  avg=5.02

топ-10 пользователей и их шард:
  user_id=25      заказов=20   shard=2
  user_id=1       заказов=18   shard=2
  user_id=41      заказов=17   shard=0
  user_id=14328   заказов=17   shard=1
  user_id=10      заказов=17   shard=2
```

Здесь топовый пользователь всего в 4 раза активнее среднего — не страшно.
Но заметьте: трое из пяти самых активных попали на shard 2, и это чистая
случайность хеш-функции. При большем разбросе активности такое совпадение
и создаёт hot shard. В B2B-сервисе с `organization_id` один крупный клиент
легко даёт 40 % трафика — и хеш не может его «разделить», потому что все
его данные обязаны лежать вместе.

**Определённый тип запросов.** Даже при идеальном распределении данных
запросы бывают разной стоимости. `GET /users/{id}/orders?limit=20` — это
Index Scan на 9 строк. А аналитический отчёт по одному крупному клиенту —
это агрегация по десяткам тысяч строк. Один шард может быть завален
тяжёлыми запросами, имея ровно столько же строк, сколько соседи.

### Почему равное количество строк на shard'ах ещё не означает равномерную нагрузку

Потому что это две разные величины, и хеш-функция управляет только первой.

Router распределяет **ключи**, а нагрузку создают **обращения к ключам**.
Связи между ними нет никакой: у пользователя может быть один заказ и сто
запросов в минуту, а может быть двадцать заказов и ни одного запроса за
месяц. Хеш `blake2b(user_id)` про активность пользователя ничего не знает —
он видит только само значение ключа.

Три независимых измерения, которые расходятся:

| Что распределяем | Чем управляет router | Измерено |
|---|---|---|
| Строки | напрямую | 32.32 / 33.45 / 34.23 % |
| Запросы (QPS) | никак | зависит от поведения пользователей |
| Стоимость запроса (CPU, I/O) | никак | зависит от размера данных под ключом |

Плюс эффект, специфичный для co-location: все данные одного ключа обязаны
лежать на одном узле — в этом и смысл шардирования по `user_id`. Значит,
нагрузку одного ключа **принципиально нельзя разделить** между шардами.
Если один ключ генерирует 40 % трафика, один шард получит 40 % нагрузки, и
это не чинится ни виртуальными узлами, ни сменой хеш-функции.

Что с этим делают на практике: выносят горячий ключ на выделенный шард
(таблица исключений в router'е поверх хеша), ставят реплику под чтение
конкретно горячему шарду, кэшируют его горячие ответы, либо меняют ключ
на более дробный (например, `(user_id, месяц)` — но это ломает
single-shard запросы по всей истории пользователя).

## 8. Итоговый анализ shard key

### Подходит ли `orders.user_id` для этого сервиса?

**Да.** Он оптимален для того профиля нагрузки, который у сервиса есть
сейчас, и при этом честно ломает часть аналитики — но эта часть и так
переносится в офлайн.

### Плюсы: какие запросы стали эффективными

| Запрос | shards_queried | Медиана |
|---|---|---|
| Заказы пользователя | 1 | 0.73 мс |
| Статистика пользователя (`COUNT/SUM/AVG`) | 1 | 0.65 мс |
| Заказ с позициями (`JOIN order_items`) | 1 | 0.86 мс (на шарде) |
| Создание заказа | 1 | — |

Это и есть основной трафик магазина: почти всё, что делает живой
пользователь, ключ содержит. Каждый такой запрос идёт **на один узел**,
выполняется обычным SQL по обычному индексу и при росте кластера не
замедляется вообще: десять шардов вместо трёх — то же самое время ответа,
только каждый узел хранит втрое меньше.

Отдельный плюс — `orders JOIN order_items` остался локальным, вместе с
работающим FK. Это прямое следствие co-location по одному ключу.

### Минусы: какие запросы стали распределёнными

| Запрос | shards_queried | Что ломается |
|---|---|---|
| `COUNT(*)`, `GROUP BY status` | 3 | нужна склейка, `AVG` пересчитывается |
| `ORDER BY created_at LIMIT 100` | 3 | 300 строк по сети ради 100 |
| Поиск заказа по `id` | 3 | router бесполезен: `id` — не shard key |
| `orders JOIN users` | 3 + 1 | JOIN руками в приложении |
| `sales_by_category` | — | не выражается вообще: `products` в другой базе |
| Список заказов по `status` | 3 | фильтр не связан с ключом |

Самый обидный пункт — поиск по `id`. `GET /api/orders/{id}` выглядит как
простейший запрос, а после шардирования опрашивает весь кластер (2.35 мс
против 0.73 мс у single-shard) и при отказе узла может ложно ответить
«не найдено». Лечится составным публичным идентификатором вида
`{user_id}-{order_id}`, который несёт в себе shard key.

### Проблемные операции

| Операция | Сложность | Почему |
|---|---|---|
| **JOIN** | высокая | с `users`/`products` — только вручную в приложении; `orders JOIN order_items` спасён co-location |
| **Aggregation** | средняя | `COUNT/SUM` складываются, `AVG` пересчитывается, `COUNT(DISTINCT)` и медиана — точно не считаются в принципе |
| **ORDER BY** | средняя | `N × шардов` строк по сети; `OFFSET` деградирует катастрофически |
| **Migration** | **самая высокая** | `ALTER TABLE` надо прогнать на каждом узле, атомарности нет: кластер какое-то время живёт с разными схемами |
| **Backup** | высокая | N независимых дампов, снятых в разное время. Согласованного на один момент снимка всего кластера нет вообще |
| **Восстановление** | высокая | восстановили один шард из вчерашнего дампа — получили кластер, где треть данных из вчера, а две трети из сегодня |
| **Балансировка** | средняя | благодаря Consistent Hashing — 22 % переезда вместо 74.81 %, но всё равно ручная операция с двойной записью |

Отдельно стоит отметить **транзакции**. Здесь они не пострадали, и опять
из-за удачного ключа: транзакция «создать заказ + позиции» целиком
укладывается в один шард. Если бы `order_items` шардировались по
`product_id`, понадобился бы двухфазный коммит — и вот это была бы самая
тяжёлая позиция в таблице.

## Вывод

**Если бы я проектировал систему заново, оставил бы `user_id`.**

Причина в том, что выбор shard key — это выбор, какие запросы останутся
дешёвыми, а не попытка сделать дешёвыми все. Сервис — интернет-магазин,
его трафик состоит из «покажи мои заказы», «покажи мой заказ», «создай
заказ». Все три содержат `user_id`, и после шардирования все три остались
обычным локальным SQL на 0.7 мс. Ломается аналитика — но она и в
нешардированном виде выполнялась секундами, её нормальное место — офлайн,
в предпосчитанных витринах, а не в онлайн-запросе.

Что я изменил бы, не трогая сам ключ:

1. **Составной публичный `id` заказа** — `{user_id}-{order_id}` вместо
   голого числа. Это убрало бы единственный по-настоящему неприятный
   распределённый запрос: поиск по id перестал бы опрашивать весь кластер.
2. **Шардировать `users` тем же ключом** (`users.id`). Тогда
   `orders JOIN users` стал бы локальным и ручная склейка исчезла бы.
3. **`products` и `categories` — как reference table**, копией на каждом
   шарде. Справочник маленький (4 040 товаров), зато `orders JOIN products`
   перестал бы быть невыразимым.
4. **Keyset-пагинация везде вместо OFFSET.** На одной базе это была
   оптимизация, в распределённом виде — необходимость.

Что действительно требовало бы другого ключа: если бы сервис стал B2B, где
один клиент даёт десятки процентов трафика. Тогда ни `user_id`, ни
`organization_id` не спасают — любой ключ, по которому данные обязаны лежать
вместе, делает крупного клиента hot shard'ом. Там пришлось бы либо
выделять крупных клиентов на персональные шарды, либо дробить ключ
(`(user_id, период)`), жертвуя запросами по всей истории.

## Вопросы для самопроверки

**1. Чем single-shard query отличается от distributed query?**
В single-shard запросе есть shard key, поэтому router вычисляет адрес и идёт
на один узел: обычный SQL, обычный индекс, 0.73 мс, `shards_queried: 1`.
В distributed query ключа нет, адрес неизвестен, и приходится опрашивать
все узлы и склеивать ответы в приложении: `shards_queried: 3`, плюс
накладные расходы на слияние и риск частичного ответа.

**2. Почему JOIN между shard'ами сложнее обычного JOIN?**
Потому что его делает не СУБД, а приложение. Обычный JOIN — это работа
планировщика: он знает статистику, выбирает nested loop / hash / merge,
проталкивает условия вниз. Между шардами ничего этого нет: нужно вручную
забрать левую сторону, собрать ключи, отдельным запросом забрать правую,
склеить — и заранее решить, влезет ли это в память. Плюс теряется FK: в
проекте уцелел единственный FK — `order_items → orders`, и только потому,
что таблицы колокированы.

**3. Как выполнить COUNT(*) по всем shard'ам?**
`SELECT COUNT(*)` на каждом шарде параллельно, затем сложить результаты в
приложении (`app/sharding/queries.py: all_orders_count`). Измерено:
32 319 + 33 449 + 34 232 = 100 000 за 3.56 мс. Важно: так складываются
только `COUNT`, `SUM`, `MIN`, `MAX`. `AVG` нужно пересчитывать из `SUM/COUNT`,
а `COUNT(DISTINCT)` таким способом не считается вовсе — одно значение может
встретиться на нескольких шардах.

**4. Почему ORDER BY ... LIMIT требует объединения результатов?**
Потому что порядок глобальный, а данные разложены по узлам без учёта этого
порядка: `created_at` в маршрутизации не участвует. Сто самых свежих заказов
могут оказаться на любом из шардов в любой пропорции. Поэтому берём top-N с
каждого (запись, не вошедшая в top-N своего шарда, в глобальный top-N попасть
не может) и отрезаем первые N после слияния. Цена — 300 строк по сети ради
100 нужных.

**5. Что произойдёт при отказе одного shard?**
Проверено: `docker stop shop_shard2`. Треть данных (34 232 заказа,
6 836 пользователей) стала недоступна; single-shard запросы к этим
пользователям отдают **503**; распределённые отвечают **200 с
`partial: true`** и неполной суммой (65 768 вместо 100 000); запросы к
пользователям других шардов и вся основная база работают нормально. Кольцо
при этом остаётся трёхшардовым — убирать упавший узел из router'а нельзя,
иначе после возвращения записи «потеряются».

**6. Что такое hot shard?**
Шард, на который приходится непропорционально много нагрузки. Возникает не
от количества строк, а от обращений: один активный ключ может нагружать узел
сильнее тысячи спящих. В проекте распределение строк 32.32 / 33.45 / 34.23 %,
но три из пяти самых активных пользователей случайно попали на shard 2 — при
большем разбросе активности этого достаточно для перекоса.

**7. Почему выбор shard key влияет на JOIN?**
Потому что JOIN локален ровно тогда, когда обе стороны лежат на одном узле,
а это определяется ключом. Здесь `order_items` получили тот же shard key,
что и `orders`, — и JOIN остался обычным SQL с работающим FK
(`Nested Loop`, 0.855 мс). А `users` шардированы не были — и тот же по
смыслу JOIN превратился в четыре round-trip и ручную склейку.

**8. Какие операции особенно плохо подходят для распределённых данных?**
`COUNT(DISTINCT)`, медианы и перцентили — их вообще нельзя посчитать точно
без переноса всех значений. `ORDER BY ... OFFSET` — при `OFFSET 10000`
понадобится 30 300 строк ради 100. Миграции схемы — нет атомарности между
узлами. Согласованный бэкап всего кластера — не существует в принципе.
Транзакции на несколько шардов — требуют двухфазного коммита (в этом проекте
их нет благодаря co-location).

**9. Что произойдёт при изменении количества shard'ов?**
Часть данных меняет адрес, и сколько именно — зависит от стратегии. Измерено
на 100 000 заказов при переходе 3 → 4: `hash % N` перемещает **74.81 %**,
Consistent Hashing — **22.00 %**. Подробный разбор — лабораторная №5,
задания 5 и 7.

**10. Чем шардирование отличается от репликации?**
Репликация (лабораторная №4) копирует **одни и те же** данные на несколько
узлов: масштабирует чтение, даёт отказоустойчивость, объём данных на узле не
уменьшает. Шардирование **делит** данные: масштабирует и запись, и объём, но
отказоустойчивость только ухудшает — отказ узла означает потерю доступа к
его части. Это ортогональные механизмы, и в продакшене их применяют вместе:
шардируют, а затем каждому шарду дают реплику.

**11. Может ли шардирование сделать отдельный SQL-запрос быстрее?**
Да, но косвенно — за счёт того, что на узле лежит меньше данных: индексы
компактнее, кэш эффективнее, `Seq Scan` короче втрое. Распределённый запрос
при этом ещё и выполняется параллельно, и время равно максимуму, а не сумме
(замер с `pg_sleep(0.1)`: 103.7 мс на трёх шардах против 306.8 мс
последовательно). Но сам по себе single-shard запрос на 9 строках по индексу
быстрее не станет — он и до шардирования был 0.7 мс. И появляются новые
расходы: сетевой round-trip до каждого узла, слияние результатов, 300 строк
вместо 100 в `ORDER BY ... LIMIT`. На маленьких точечных запросах
шардирование скорее чуть замедляет; выигрыш оно даёт на объёме и на
пропускной способности, а не на латентности отдельного простого запроса.
