# Лабораторная работа №5. Шардирование PostgreSQL: Router и Consistent Hashing

Работа выполнена на собственном сервисе (`Shop API`, FastAPI + psycopg3 + PostgreSQL 16).
Никаких отдельных учебных таблиц не создавалось: шардируется реальная растущая
сущность проекта — `orders` — и её реальные данные.

Что появилось в коде:

| Файл | Роль |

| `app/sharding/pools.py` | по пулу соединений на каждый PostgreSQL |
| `app/sharding/queries.py` | single-shard и scatter-gather запросы |

| `scripts/shard_admin.py` | CLI: init / load / stats / rebalance / route / demo |
| `docker-compose.yml` | сервисы `shard0`…`shard3` |

## 1. Выбор данных для шардирования

### 1. Какую сущность выбрал

**`orders`** — заказы. Это основная растущая таблица сервиса: в основной базе
их сейчас 5 000 300 против 20 053 пользователей и 4 040 товаров. Шардировать
имеет смысл именно то, что растёт без потолка; справочники (`users`,
`products`, `categories`) растут медленно и помещаются на один узел.

Вместе с заказами на тот же шард едут `order_items` — они бессмысленны в
отрыве от своего заказа.

### 2. Какое поле используется как shard key

**`orders.user_id`.**

Для `order_items` shard key тот же: при загрузке в шард позиции получают
денормализованное поле `user_id`, скопированное из заказа. Это техника
co-location: связанные строки гарантированно оказываются на одном узле.

### 3. Почему выбран именно этот ключ

Три причины.

**Он есть почти в каждом запросе сервиса.** Реальные запросы из
`app/repositories/orders.py` и `app/repositories/analytics.py`:

```sql
-- список заказов пользователя
WHERE o.user_id = %s ORDER BY o.created_at DESC LIMIT %s OFFSET %s
-- статистика по пользователю
LEFT JOIN orders o ON o.user_id = u.id AND o.status <> 'CANCELLED' WHERE u.id = %s
-- создание заказа
INSERT INTO orders (user_id) VALUES (%s)
```

Если ключ есть в `WHERE`, router знает адрес и запрос идёт на один шард.

**Он не меняется.** Заказ никогда не переходит другому пользователю, поэтому
запись не «переезжает» между шардами при обновлении. Если бы ключом был
`status`, каждая смена статуса (`NEW → PAID → SHIPPED`) означала бы физический
перенос строки на другой узел.

**Он даёт естественную co-location.** Все заказы одного пользователя лежат
рядом, поэтому «мои заказы», «моя статистика», «мой заказ с позициями» — это
обычный локальный SQL, а не распределённый запрос.

Почему **не** `orders.id`: он растущий и последовательный. По хешу он бы
распределился ровно, но заказы одного пользователя разлетелись бы по всем
шардам, и главный запрос сервиса стал бы распределённым. А без хеша (range по
id) весь новый трафик писался бы в последний шард.

Почему **не** `created_at`: та же проблема — все сегодняшние записи на одном
шарде, это заведомый hot shard. По времени данные уже разрезаны партициями
внутри основной базы (лабораторная №3), вторым таким же разрезом ничего не
выигрываешь.

### 4. Насколько равномерно он распределяет данные

Ожидание: достаточно равномерно, но не идеально, и по двум разным причинам.

*По количеству ключей* — равномерно: `user_id` это 20 тысяч независимых
значений, хеш размазывает их ровно.

*По количеству строк* — хуже: у пользователей разное число заказов. Факт по
загруженной выборке:

```
заказов на пользователя: min=1  max=20  avg=5.02
```

Разброс всего 20×, поэтому на 20 тысячах ключей закон больших чисел
сглаживает перекос. Но если бы сервис был B2B и ключом был `organization_id`,
где одна организация даёт 40 % заказов, — один шард забрал бы эти 40 % и никакое
хеширование не помогло бы.

### 5. Какие запросы сервиса используют этот ключ

| Запрос | Где в коде | Использует shard key |
|---|---|---|
| `GET /api/orders?user_id=...` | `repositories/orders.py: list_orders` | да |
| `POST /api/orders` | `repositories/orders.py: create` | да |
| `GET /api/analytics/users/{id}` | `repositories/analytics.py: user_stats` | да |
| `GET /api/orders/{id}` | `repositories/orders.py: get_by_id` | **нет** (id, не user_id) |
| `GET /api/analytics/sales-by-category` | `repositories/analytics.py` | **нет** (агрегат по всем) |
| `GET /api/orders?status=PAID` | `repositories/orders.py: list_orders` | **нет** |

То есть пользовательская часть API после шардирования остаётся single-shard,
а аналитическая и административная становится распределённой. Подробный
разбор — в лабораторной №6.

## 2. Запуск нескольких PostgreSQL

Поднято **четыре** независимых экземпляра (три рабочих + один для
эксперимента с расширением кластера). Фрагмент `docker-compose.yml`:

```yaml
  shard0: &shard
    image: postgres:16-alpine
    container_name: shop_shard0
    environment:
      POSTGRES_USER: shard
      POSTGRES_PASSWORD: shard
      POSTGRES_DB: shard
    ports:
      - "${SHARD0_HOST_PORT:-5440}:5432"
    volumes:
      - shard0_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U shard -d shard"]

  shard1:
    <<: *shard
    container_name: shop_shard1
    ports: ["${SHARD1_HOST_PORT:-5441}:5432"]
    volumes: [shard1_data:/var/lib/postgresql/data]
  # shard2, shard3 — аналогично
```

| Контейнер | Порт на хосте | Роль |
|---|---|---|
| `shop_shard0` | 5440 | shard 0 |
| `shop_shard1` | 5441 | shard 1 |
| `shop_shard2` | 5442 | shard 2 |
| `shop_shard3` | 5443 | резерв для эксперимента «3 → 4» |

Важно: между шардами **нет** ни репликации, ни общих транзакций, ни FDW.
Это не кластер, а четыре ничего не знающих друг о друге PostgreSQL. Всё
связывание происходит в приложении.

Backend видит их через `SHARD_URLS` — порядок URL задаёт номера шардов:

```yaml
SHARD_URLS: "postgresql://shard:shard@shard0:5432/shard,\
             postgresql://shard:shard@shard1:5432/shard,\
             postgresql://shard:shard@shard2:5432/shard"
```

`shard3` поднят, но в список не включён — он подключается только в
экспериментах заданий 5 и 7.

### Схема шарда

`migrations_shard/001_shard_init.sql` отличается от основной схемы тремя
вещами, и каждое отличие — прямое следствие того, что шарды независимы:

1. **Нет `users`, `products`, `categories`.** Они не шардируются. Значит,
   `FOREIGN KEY (user_id) REFERENCES users(id)` физически невозможен: чужая
   таблица лежит в другом PostgreSQL. Целостность здесь обеспечивает
   приложение, а не СУБД.
2. **`id BIGINT`, а не `BIGSERIAL`.** Значения приезжают из основной базы и
   должны с ней совпадать. Своя последовательность на каждом шарде рано или
   поздно выдала бы одинаковый `id` на разных узлах.
3. **`order_items.user_id`** — денормализованный shard key, чтобы позиции
   лежали на том же шарде, что и заказ.

Индексы на шарде:

```sql
CREATE INDEX idx_shard_orders_user_created ON orders (user_id, created_at DESC);
CREATE INDEX idx_shard_orders_created      ON orders (created_at DESC);
CREATE INDEX idx_shard_order_items_order   ON order_items (order_id);
```

Первый обслуживает single-shard запросы, второй нужен для распределённого
`ORDER BY created_at DESC LIMIT N` — иначе каждый шард делал бы Seq Scan.

## 3. Реализация Router

Интерфейс один, стратегий две (`app/sharding/router.py`):

```python
class ShardRouter:
    def route(self, key: object) -> int: ...


class ModuloRouter(ShardRouter):
    """shard = hash(key) % N."""
    def route(self, key):
        return self.shard_ids[hash_key(key) % len(self.shard_ids)]
```

Функция хеширования:

```python
def hash_key(key: object) -> int:
    digest = hashlib.blake2b(str(key).encode("utf-8"), digest_size=8).digest()
    return int.from_bytes(digest, "big")
```

**Почему не встроенный `hash()`.** В Python хеш строк солится случайным
значением при каждом старте процесса (`PYTHONHASHSEED`). После рестарта
backend та же запись поехала бы на другой шард, и данные стали бы
«невидимыми». Нужна функция, которая даёт один и тот же результат всегда и
во всех процессах, — отсюда `hashlib`.

Проверка работы router:

```
$ docker compose exec backend python -m scripts.shard_admin route 42
shard key: 42
hash:      6319743179241711738
шардов:    3
  modulo       -> shard 0
  consistent   -> shard 1
```

Тот же ответ отдаёт API:

```
GET /api/shards/route/42
```

Router подключён к пулам (`app/sharding/pools.py`) — приложение никогда не
выбирает соединение руками:

```python
@contextmanager
def connection_for(key: object) -> Iterator[Connection]:
    """Соединение с тем шардом, где живёт запись с этим shard key."""
    with shard_connection(route(key)) as conn:
        yield conn
```

### Выводы

**Насколько равномерно.** Очень равномерно: 33.50 / 32.93 / 33.56 % при
идеале 33.33 %. Отклонение от идеала — 0.4 процентных пункта. Число уникальных
пользователей на шардах тоже почти совпадает (6685 / 6557 / 6676).

**Есть ли заметный дисбаланс.** Разница между самым большим и самым маленьким
шардом — 629 заказов, то есть 1.89 % от среднего. Для 100 тысяч записей это
шум.

**Может ли такой дисбаланс стать проблемой.** Сам по себе — нет. 2 % перекоса
не заметит ни диск, ни CPU. Проблемой становится другое:

- дисбаланс **по нагрузке**, а не по строкам. Здесь у топового пользователя
  20 заказов при среднем 5 — разброс мал. Но если бы один клиент давал 30 %
  трафика, хеш отправил бы все его запросы на один узел, и строки при этом
  всё равно были бы распределены ровно (разбор — лабораторная №6, задание 7);
- дисбаланс, который **нельзя исправить**: чтобы разгрузить шард, данные надо
  перевезти, а при `hash % N` любое изменение N перетасовывает почти всё
  (задание 5).

## 5. Что произойдёт при добавлении нового shard

Эксперимент на том же наборе из 100 000 заказов (19 918 уникальных `user_id`):

```
$ docker compose exec backend python -m scripts.shard_admin rebalance --limit 100000 --frm 3 --to 4

ключей (user_id): 19918, строк (orders): 100000
переход: 3 shards -> 4 shards

--- hash(key) % N ---
  было:  ['33503 (33.50%)', '32934 (32.93%)', '33563 (33.56%)']
  стало: ['25137 (25.14%)', '24951 (24.95%)', '24763 (24.76%)', '25149 (25.15%)']
  переехало ключей: 14940 из 19918 (75.01 %)
  переехало строк:  74807 из 100000 (74.81 %)
  осталось на месте: 25193 (25.19 %)
```

| | Значение |
|---|---|
| Всего записей | 100 000 |
| Новый shard | Shard 3 |
| Изменили shard | **74 807 (74.81 %)** |
| Не изменили | 25 193 (25.19 %) |

### Вывод: почему добавление одного PostgreSQL перемещает так много данных

Потому что в формуле `shard = hash(key) % N` число шардов **входит в сам
адрес**. Это не «указатель на узел», а вычисление, целиком зависящее от N.
Меняя N, мы меняем функцию, а не добавляем ветку к старой.

Конкретно: остаток от деления на 3 и остаток от деления на 4 — величины
независимые. Запись останется на месте только если случайно совпали оба
остатка, а вероятность этого примерно 1/4. Отсюда и 25 % оставшихся,
74.81 % переехавших — почти в точности теоретические 75 %.

Что это значит на практике: чтобы добавить один узел к трём, нужно
физически перевезти три четверти базы. На 100 тысячах строк это 19 секунд,
на реальных 5 миллионах заказов — уже совсем другой разговор, и всё это время
система либо недоступна на запись, либо работает в режиме двойной записи с
ручной сверкой. Именно поэтому `hash % N` практически не встречается в
системах, которые планируют расти.

## 6. Реализация Consistent Hashing

```python
class ConsistentHashRouter(ShardRouter):
    def __init__(self, shard_ids, virtual_nodes: int = 150):
        self._ring: List[int] = []          # отсортированные точки кольца
        self._owner: Dict[int, int] = {}    # точка -> shard_id
        for shard_id in shard_ids:
            for vnode in range(virtual_nodes):
                point = hash_key(f"shard-{shard_id}#{vnode}")
                if point not in self._owner:
                    self._owner[point] = shard_id
                    self._ring.append(point)
        self._ring.sort()

    def route(self, key):
        point = hash_key(key)
        idx = bisect.bisect_right(self._ring, point)
        if idx == len(self._ring):
            idx = 0                          # кольцо замкнуто
        return self._owner[self._ring[idx]]
```

Идея в трёх строчках:

1. Пространство хешей (0 … 2⁶⁴−1) сворачивается в кольцо: после последнего
   значения идёт первое.
2. Каждый шард ставит на кольцо свои точки — не одну, а `virtual_nodes`
   штук, с именами `shard-0#0`, `shard-0#1`, …
3. Ключ хешируется в точку кольца и отдаётся **первому шарду по часовой
   стрелке**. Поиск — бинарный (`bisect`), то есть O(log(N·V)).

**Ключевое отличие от `% N`: число шардов не входит в формулу адреса.**
Адрес ключа — это «ближайшая точка справа». Когда добавляется новый шард, он
вставляет свои точки в кольцо и забирает только те ключи, которые лежат на
дугах непосредственно перед его точками. Все остальные дуги не тронуты, и
их ключи не двигаются вообще.

### Зачем виртуальные узлы

Если у каждого шарда одна точка, три случайных числа делят кольцо на три
очень неравные дуги. Измерено на тех же 100 000 заказов:

```
 vnodes   shard0   shard1   shard2   разброс max-min
      1   77.21%    8.77%   14.03%    68.44 п.п.
      5   21.62%   38.84%   39.55%    17.93 п.п.
     20   31.48%   38.18%   30.34%     7.84 п.п.
     50   34.56%   33.92%   31.52%     3.04 п.п.
    150   32.32%   33.45%   34.23%     1.91 п.п.
    500   32.74%   33.30%   33.95%     1.21 п.п.
```

При одной точке на шард shard 0 забрал **77 % данных** — стратегия
неработоспособна. Каждый шард с сотней точек владеет сотней маленьких дуг,
их суммарная длина усредняется, и распределение выравнивается. В проекте по
умолчанию `SHARD_VIRTUAL_NODES=150` — разброс 1.91 п.п., практически как у
`% N` (1.89 п.п.), но без его главного недостатка.

Плата за виртуальные узлы: кольцо из 450 точек вместо 3 и `O(log n)` вместо
одного деления. На фоне сетевого round-trip в PostgreSQL это не измеримо.

## 7. Сравнение стратегий

Тот же эксперимент 3 → 4 шарда, тот же набор данных:

```
--- Consistent Hashing ---
  было:  ['32319 (32.32%)', '33449 (33.45%)', '34232 (34.23%)']
  стало: ['23617 (23.62%)', '25788 (25.79%)', '28592 (28.59%)', '22003 (22.00%)']
  переехало ключей: 4324 из 19918 (21.71 %)
  переехало строк:  22003 из 100000 (22.00 %)
  осталось на месте: 77997 (78.00 %)
```

### Результат

| Стратегия | Перемещено |
|---|---|
| `hash(key) % N` | **74.81 %** |
| Consistent Hashing | **22.00 %** |

Разница — **3.4 раза**.

### 1. Почему результаты отличаются

Потому что это два разных способа ответить на вопрос «где лежит ключ».

`hash % N` вычисляет адрес **через количество узлов**. N — часть формулы,
и смена N переопределяет функцию целиком; сохранение адреса — случайность
с вероятностью ~1/N_new.

Consistent Hashing вычисляет адрес **через положение на кольце**.
Количество узлов в вычислении не участвует вообще. Добавление шарда — это
вставка новых точек, которая затрагивает только соседние дуги. Позиция всех
остальных ключей относительно всех остальных точек не изменилась, значит и
владелец у них тот же.

### 2. Почему Consistent Hashing уменьшает объём перемещения

Новый шард забирает только те ключи, которые попадают на его собственные
дуги. Суммарная длина этих дуг примерно равна его доле кольца, то есть
1/(N+1). При переходе 3 → 4 это ≈ 25 %.

Измерено 22.00 % — чуть меньше теоретических 25 %. Причина: дуги не идеально
равны. Видно по итоговому распределению — 23.62 / 25.79 / 28.59 / 22.00 %.
Четвёртый шард встал на дуги чуть короче средних, поэтому забрал 22 %, а не
25 %. Обратная сторона той же монеты — разброс распределения после
расширения вырос (у `% N` стало ровно 25 / 25 / 25 / 25 %). Это честный
компромисс: Consistent Hashing меняет идеальную равномерность на дешёвое
расширение, и при необходимости равномерность добирается увеличением
`virtual_nodes`.

Главное же — что переезжает. У `% N` 74.81 % данных меняют шард, причём
переезжают они **между старыми узлами**: ключ с shard 0 может уехать на
shard 1, хотя ни один из них не новый. Это чистая бессмысленная работа.
У Consistent Hashing все 22 % едут строго в одну сторону — на новый шард.
Старые узлы между собой не обмениваются ничем.

### 3. Что произойдёт, если добавить ещё один shard

4 → 5, тот же набор данных:

```
hash(key) % N         79.75 %
Consistent Hashing    22.10 %
```

У `% N` стало ещё хуже: теоретический остаток на месте — 1/5, то есть
переезжает уже ~80 %. У Consistent Hashing — те же ~22 %, и дальше доля
будет медленно снижаться как 1/(N+1): при 10 шардах переедет ~9 %.

То есть стоимость расширения у `% N` растёт с размером кластера, а у
Consistent Hashing — падает. Это и есть причина, по которой вторую стратегию
выбирают все, кто собирается расти.

### 4. Что произойдёт, если удалить shard

4 → 3 (убрали последний шард):

```
hash(key) % N         74.81 %
Consistent Hashing    22.00 %
```

Симметрично добавлению. У `% N` удаление узла снова перетасовывает три
четверти базы. У Consistent Hashing исчезают точки удалённого шарда, и его
дуги переходят следующим по часовой стрелке соседям — переезжают только его
собственные ~22 % данных, остальные 78 % не двигаются.

Отдельно важно: **упавший** шард удалять из кольца нельзя.
Если убрать точки временно недоступного узла, ключи начнут маршрутизироваться
к соседям, запишутся туда, а после возвращения шарда router вернёт их обратно
— и записи «потеряются». Поэтому в сервисе отказ шарда обрабатывается иначе:
кольцо не меняется, запрос к мёртвому узлу отдаёт 503 (см. лабораторную №6,
задание 6):

```
shop_backend | ERROR app.sharding.pools: shard 2 недоступен: pool initialization incomplete after 20 sec
shop_backend | INFO  app.sharding.pools: router: <ConsistentHashRouter shards=[0, 1, 2]>
```

Кольцо по-прежнему из трёх шардов, хотя доступно два.

## 8. Итог

**Shard** — самостоятельный экземпляр базы, который хранит только часть
данных. Шардов несколько, вместе они держат весь набор, но ни один из них
не знает, что лежит у соседей, и SQL-запрос к одному шарду видит только его
кусок. **Shard key** — поле, по которому вычисляется, на каком именно шарде
живёт запись; в этом проекте это `orders.user_id`, и на него же «подвешены»
`order_items`, чтобы связанные строки лежали вместе. **Router** нужен потому,
что сама база ничего о шардировании не знает: кто-то должен по ключу
посчитать адрес и выбрать соединение — этим занимается `app/sharding/router.py`
вместе с `pools.py`, а репозитории просто получают готовое соединение.
Простейшая стратегия `hash(key) % N` распределяет данные почти идеально
(33.50 / 32.93 / 33.56 % на трёх шардах), но у неё есть встроенная проблема:
число шардов входит в формулу адреса, поэтому при переходе 3 → 4 переехало
**74.81 %** всех записей, а при 4 → 5 переехало бы уже ~80 %. Consistent
Hashing считает адрес как ближайшую точку на кольце хешей, и количество
узлов в этом вычислении не участвует, поэтому тот же переход 3 → 4 сдвинул
только **22.00 %** данных, причём строго в сторону нового шарда. Ровность
при этом обеспечивают виртуальные узлы: с одной точкой на шард распределение
получилось 77 / 9 / 14 %, со 150 точками — 32.3 / 33.5 / 34.2 %. Для своего
сервиса я выбрал **Consistent Hashing** (`SHARD_STRATEGY=consistent`):
равномерность у него практически такая же, как у `% N` (разброс 1.91 против
1.89 п.п.), а расширение кластера стоит в 3.4 раза дешевле — и чем больше
узлов, тем больше эта разница.

## Вопросы для самопроверки

**1. Что такое shard?**
Отдельный, полностью самостоятельный экземпляр базы, хранящий часть общего
набора данных. В этом проекте — четыре независимых PostgreSQL 16 в Docker
(`shop_shard0`…`shop_shard3`). Между ними нет ни репликации, ни общих
транзакций: заказ, лежащий на shard 1, для shard 0 не существует.

**2. Что такое shard key?**
Поле, из которого вычисляется номер шарда. Здесь `orders.user_id`. Ключ
должен быть неизменяемым (заказ не меняет владельца) и присутствовать в
большинстве запросов — иначе router не сможет определить адрес.

**3. Почему нельзя просто случайно распределять записи между PostgreSQL?**
Потому что тогда запись нельзя будет **найти**. Распределение обязано быть
детерминированной функцией от ключа: положили по формуле — читаем по той же
формуле. При случайной раскладке любой `SELECT` превращался бы в опрос всех
шардов, а `UPDATE` — в поиск записи по всему кластеру. Отсюда же требование
к хеш-функции: `hashlib`, а не `hash()`, потому что второй солится при каждом
старте процесса и после рестарта «терял» бы данные.

**4. Как работает hash(key) % N?**
Ключ превращается в число (`blake2b` → 64 бита), берётся остаток от деления
на количество шардов, остаток и есть номер шарда. Дёшево (одно деление) и
равномерно, потому что хеш равномерен, а остаток наследует эту равномерность.

**5. Почему изменение количества shard'ов является проблемой?**
Потому что N входит в формулу адреса. Остаток по модулю 3 и остаток по модулю
4 — независимые величины, совпадают примерно у 1/4 ключей. Измерено:
при 3 → 4 переехало 74.81 % записей, причём значительная их часть — между
старыми шардами, без всякой пользы. Это часы или сутки миграции при
недоступной на запись системе.

**6. Что такое Consistent Hash Ring?**
Пространство хешей, замкнутое в кольцо: после 2⁶⁴−1 идёт 0. На кольцо
ставятся точки шардов, ключ хешируется в свою точку и отдаётся первому
шарду по часовой стрелке. Адрес определяется взаимным расположением точек,
а не их количеством.

**7. Почему при добавлении shard'а не приходится переносить все данные?**
Новый шард вставляет свои точки в существующее кольцо и забирает только
ключи с дуг непосредственно перед ними — примерно 1/(N+1) кольца. Для всех
остальных ключей ближайшая точка справа не изменилась, значит и владелец
прежний. Измерено: 22.00 % вместо 74.81 %.

**8. Что такое virtual nodes и зачем они нужны?**
Каждый шард представлен на кольце не одной точкой, а множеством
(`shard-0#0`, `shard-0#1`, …). Нужны для равномерности: три случайные точки
делят кольцо на очень неравные дуги. Измерено на реальных данных —
при одной точке на шард распределение 77.21 / 8.77 / 14.03 %, при 150 точках
32.32 / 33.45 / 34.23 %. Побочный плюс: при удалении шарда его сотня дуг
расходится по всем соседям, а не сваливается целиком на одного.

**9. Может ли Consistent Hashing гарантировать идеальное распределение
нагрузки?**
Нет, и это видно прямо в измерениях. Даже по строкам остаётся разброс
1.91 п.п., а после расширения до 4 шардов — 22.00 / 23.62 / 25.79 / 28.59 %.
Виртуальные узлы уменьшают разброс, но не обнуляют его. И это только
распределение **данных**; распределение **запросов** хеш не контролирует
вообще: один активный пользователь может давать больше нагрузки, чем тысяча
спящих, а лежат они на разных шардах в пропорции, которую никто не выбирал.

**10. Что произойдёт, если один shard станет значительно более загруженным
остальных?**
Он станет узким местом всей системы: время ответа по его ключам вырастет, а
остальные узлы будут простаивать. Общая пропускная способность кластера
определяется самым медленным шардом, поэтому «в среднем всё хорошо» ничего
не значит. Лечится это либо увеличением числа виртуальных узлов (если перекос
по данным), либо выделением горячего ключа на отдельный шард, либо сменой
shard key, либо репликой под чтение у горячего шарда. Подробный разбор
причин — лабораторная №6, задание 7.
